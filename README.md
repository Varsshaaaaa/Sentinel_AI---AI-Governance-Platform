# SentinelAI

SentinelAI is an **Autonomous AI Governance Operating System** .It governs **any** AI agent at runtime — it does **not** build agents.

Most guardrail products filter what an LLM *says*. SentinelAI controls what an agent is allowed to **do** — at the moment it tries to run a tool: delete records, send email, process a payment, call an external API. The agent must ask permission first; SentinelAI returns **allow**, **block**, **deny**, or **require human approval (HITL)** before the real tool runs.

**Autonomous Governance Loop:**

```
Observe → Analyze Behavior → Evaluate Policies → Take Governance Action → Learn & Improve
```

**Runtime pipeline (every tool call):**

```
Agent → POST /v1/tool/intercept
  → Governance hold check
  → Decision Auditor (log)
  → Agent WAF (PS-5.1)
  → Dynamic Policy Engine (PS-10.2)
  → Action Guardrails (PS-3.1)
  → Graph / Risk / EventBridge (PS-4.2, PS-1.3)
  → Decision Replay audit trail (PS-7.1)
```

**Stack:** Python 3.11 · FastAPI · AWS Lambda · DynamoDB · EventBridge · React · YAML policies · Cerebras (Agent Chat) · LiteLLM (Policy Copilot)

## Problem statements implemented

| Capability | Module | What it does |
|-----------|--------|--------------|
| Governance Graph Builder | `governance/graph_engine` | Maps agents → tools → data → policies; orphan detection; blast radius |
| Action Guardrails | `governance/runtime_guardrails` | Enforces block / HITL / warn / allow on matched policies |
| Governance-Linked Observability | `governance/observability_pipeline` | Ingests signals; SLA monitoring; agent state machine (green → suspended) |
| Agent WAF | `governance/agent_waf` | Runtime firewall for tool calls — rate, injection, sequence, scope |
| Decision Path Auditor | `governance/decision_engine` | Full session replay with PII redaction and causal timeline |
| Dynamic Policy Rules Engine | `governance/policy_engine` | YAML rules with inheritance; Copilot NL→YAML; policy sandbox |

###  Governance Graph

- **Problem:** No visibility into which agents touch which tools, data, or policies.
- **Solution:** DynamoDB adjacency-list graph updated at agent registration and on every allowed intercept (`Agent → Tool` `CALLS` edges).
- **Queries:** orphans, blast radius, dependency paths via `POST /v1/graph/query`.
- **UI:** `/graph`

###  Action Guardrails

- **Problem:** LLM text filters do not stop destructive tool calls.
- **Solution:** Synchronous enforcement — `block`, `require_hitl`, `warn`, `audit_only`, `allow`, session suspend after repeated violations.
- **UI:** `/hitl`, `/violations`

###  Governance-Linked Observability

- **Problem:** Observability logs anomalies but does not change governance state.
- **Solution:** Ingest CloudWatch/OTel signals; escalate agents to `under_review` or `suspended`; unified timeline and SLA sweep.
- **UI:** `/observability`

###  Agent WAF

- **Problem:** Need a fast runtime safety layer before business policy.
- **Solution:** Six rule types on every intercept (see [Agent WAF](#agent-waf-ps-51)).
- **UI:** `/waf` with live WebSocket feed

###  Decision Path Auditor

- **Problem:** Auditors need provable *why* for every agent action.
- **Solution:** Immutable step-by-step replay per session; optional LLM summary.
- **UI:** `/replay`

###  Dynamic Policy Engine

- **Problem:** Static allow/deny cannot express time, classification, scope, inheritance.
- **Solution:** 25+ YAML rules across 6 policy files; Policy Copilot; Governance Sandbox simulator.
- **UI:** `/policies`

## How governance works

### Single entry point

Every governed action uses one endpoint:

```
POST /v1/tool/intercept
```

**Orchestrator:** `backend/services/intercept_service.py`

| Step | Component | Example outcome |
|------|-----------|-----------------|
| 0 | Governance hold | Suspended agent → instant **block** |
| 1 | Decision Auditor | Log attempt for replay |
| 2 | Agent WAF | SQL injection in params → **deny** |
| 3 | Policy Engine | Delete >100 rows → match rule |
| 4 | Action Guardrails | Rule action → **block** / **require_hitl** / **allow** |
| 5 | Post-allow | Update graph, risk score, EventBridge event |

### WAF vs Policy vs Guardrails

| Layer | Role | Analogy |
|-------|------|---------|
| **Agent WAF** | Technical/runtime checks (rate, injection, sequence, scope) | Airport security scanner |
| **Policy Engine** | Business rules in YAML (time, role, classification, bulk limits) | Company rulebook |
| **Action Guardrails** | Final enforcement from matched policy | Security officer's decision |

WAF runs **before** policy. Policy runs **before** guardrails.

### Agent WAF

**WAF** = Web Application Firewall — adapted here as a firewall for **agent tool calls**, not browser HTTP.

| Rule type | What it catches |
|-----------|-----------------|
| `tool_scope` | Tool not registered for this agent |
| `rate_limit` | Too many calls in a time window |
| `parameter_validation` | SQL/script injection in tool params |
| `size_limit` | Payload too large (>64KB) |
| `data_scope` | Session scope mismatch |
| `sequence` | Wrong order (e.g. `payment_process` before `identity_verify`) |

### Intercept dispositions

| Disposition | Meaning | Agent should |
|-------------|---------|--------------|
| `allow` | Passed all checks | Execute the tool |
| `warn` / `audit_only` | Allowed with flag or extra logging | Execute; log the warning |
| `deny` | Blocked by **WAF** | Do not execute; show WAF reason |
| `block` | Blocked by **policy / guardrails** | Do not execute; show policy reason |
| `require_hitl` | Needs human approval | Wait for HITL ticket approval |

**Reading demo results:** `✓ stopped by governance` = **PASS** (tool correctly blocked/denied/HITL).

### Three Lambdas in production

| Lambda | Required? | Role |
|--------|-----------|------|
| `sentinelai-dev-api` | **Yes** | Full REST API — intercept, policies, graph, HITL, replay, Copilot |
| `sentinelai-dev-chat` | **Yes** (for dashboard chat) | Cerebras-powered Agent Chat — routes NL → agent tool plans → `POST /tool/intercept` |
| `sentinelai-dev-waf-ws` | No (UI enhancement) | WebSocket push for live WAF dashboard updates |

All **governance enforcement** runs in **`sentinelai-dev-api`**. The chat Lambda orchestrates LLM turns and calls the main API for every tool action; it does not replace the intercept pipeline. The WebSocket Lambda only streams WAF events to the browser.

### AWS architecture

```
Users / Agents
    ├── CloudFront → S3 (React dashboard, incl. /agent-chat)
    ├── API Gateway REST → Lambda sentinelai-dev-api (FastAPI + Mangum)
    │       ├── DynamoDB (8 tables: agents, policies, violations, audit, graph, events, governance, websocket)
    │       ├── EventBridge bus sentinelai-dev-governance
    │       └── Cerebras API (Policy Copilot, optional)
    ├── API Gateway REST → Lambda sentinelai-dev-chat (Agent Chat only)
    │       ├── Cerebras API (gemma-4-31b on public tier — NL routing + tool planning)
    │       └── calls sentinelai-dev-api POST /v1/tool/intercept per tool
    └── API Gateway WebSocket → Lambda sentinelai-dev-waf-ws
```

**Terraform** (`infrastructure/terraform/`) manages: DynamoDB, EventBridge, all three Lambdas, API Gateway, S3, CloudFront, IAM.

**Shell scripts** (`infrastructure/scripts/`) handle Lambda packaging (`package-lambda.sh` for API/WAF, `package-chat-lambda.sh` for chat), deploy helpers, and test runners.

## Agent Chat testing (Cerebras)

The dashboard includes a **governance testing entrypoint** at **`/agent-chat`** (also via the header **Test Agent Chat** button). It simulates how a real agent frontend would work: natural language is routed to the right demo agent, the LLM plans tool calls, and **every tool call hits `POST /v1/tool/intercept`** on the main API before any mock tool runs.

### Architecture

| Piece | Location |
|-------|----------|
| UI | React `frontend/src/pages/AgentChatPage.tsx` |
| Chat orchestration | `backend/services/agent_chat_service.py` |
| Chat REST routes | `POST /v1/chat`, `GET /v1/chat/suggestions`, `GET /v1/chat/llm-status` |
| Production backend | Lambda **`sentinelai-dev-chat`** (separate ~3.4 MB zip — not the 250 MB API bundle) |
| Governance | Main Lambda **`sentinelai-dev-api`** — unchanged intercept pipeline |

### Sidebar test chips

Suggestion chips are grouped so reviewers can trigger known outcomes:

| Group | Example prompt | Expected |
|-------|----------------|----------|
| **Try asking** | “Show me the latest transactions” | `allow` (normal flow) |
| **Should block / deny** | “Query transactions with DROP TABLE users; --” | `deny` (WAF `parameter_validation`) |
| **Should block / deny** | “Delete 500 financial records” | `block` (policy bulk delete) |
| **Needs approval (HITL)** | “Process a $50,000 payment…” | `require_hitl` |

Deny/block and HITL chip texts use **deterministic governance test scenarios** in `agent_chat_service.py`: the exact sidebar prompt sends a known tool payload to intercept (e.g. SQL injection in `params.q`) so WAF/policy outcomes match the governed_agent_demo suite — the LLM cannot “skip” governance with a fake success message.

After a chat session, use **Replay session** (or `/replay?session=…`) to inspect the audit trail.

## Python SDK & integration

### SDK usage

```python
from governance.adapters.client import SentinelAIClient

client = SentinelAIClient("https://dwybfyittl.execute-api.us-east-1.amazonaws.com/v1")

result = client.intercept(
    agent_id="agent-finance-001",
    session_id="session-abc",
    tool_name="db_delete",
    action_type="delete",
    tool_params={"table": "financial_records", "count": 500},
    data_scope_size=500,
)

if result.disposition == "allow":
    run_real_delete(...)
elif result.disposition == "require_hitl":
    wait_for_approval(result.ticket_id)
else:
    raise GovernanceError(result.reason)

# Replay a session
timeline = client.replay_session("demo-finance-session")
```

```python
        "tool_params": {"amount": 250.0},
        "data_scope_size": 250,
        "framework": "your_framework",
        "user_id": "user-123",
    }
})
result = resp.json()
# result["disposition"] → allow | block | deny | require_hitl
```

### Integration pattern (before every tool call)

```
your_agent wants to run a tool
     ↓
POST /v1/tool/intercept          ← ask governance FIRST
     ↓
allow / warn / audit_only  → run your real tool
block / deny               → stop, show reason
require_hitl               → pause, wait for human approval
```

Full reference implementation: top of `agent_demo/governed_agent_demo.py`.

## Troubleshooting

| Issue | Fix |
|-------|-----|
| Lambda deploy fails (size) | Unzipped API package must be <250MB; chat uses separate `package-chat-lambda.sh` (~19MB) |
| Lambda update fails (50MB) | Upload zip via S3, not direct `--zip-file` |
| Agent Chat 429 from Cerebras | Public tier RPM limit — wait ~60s; chat uses `gemma-4-31b`; avoid rapid chip spam |
| Agent Chat shows allow instead of deny on chips | Redeploy chat Lambda; deny chips use deterministic scenarios in `agent_chat_service.py` |
| Frontend stale after deploy | CloudFront invalidation; hard-refresh browser |
| **Frontend IDE errors** (missing `react`, unresolved imports) | Run `cd frontend && npm install` — `node_modules` is not shipped; errors disappear after install |
| Agent demo 403 | Kill stale server: `pkill -f "agent_demo/server.py"`; restart; use `http://127.0.0.1:8765` not `file://` |
| `/admin/seed-demo` returns 403 | Seed via CLI against DynamoDB (see Deployment section) |
| HITL count always 0 | Deploy latest Lambda; HITL persisted in `sentinelai-dev-governance` table |
| CORS errors | Ensure Lambda `CORS_ORIGINS` includes CloudFront URL |
| WAF page not live-updating | Check `VITE_WAF_WEBSOCKET_URL` in frontend build and WebSocket Lambda |
